# Подготовка задачи и доказательств для Codex

Этот короткий порядок дополняет существующие роли разработки Second Brain.
Он помогает заранее определить достаточную глубину работы и проверить результат
по фактам. Это **не новый агент**, не обязательная форма, не дополнительный
CI-gate и не изменение протокола [Night Shift](../automation/night-shift-v1.md).

Используйте [AGENTS.md](../../AGENTS.md), acceptance criteria самой Issue,
одну основную роль из [ROLE_MANIFEST.json](../../ROLE_MANIFEST.json) и
профильный навык AI Development Toolkit только при необходимости. Для обычной
задачи отдельный оркестратор не нужен.

## 1. Выбор глубины за один проход

Сначала назовите затронутое поведение, границу безопасности, ожидаемый
наблюдаемый результат и способ его проверки. Выберите **наиболее высокий**
подходящий уровень, не оценивая сложность по числу файлов.

| Уровень | Когда выбирать | Достаточный объём подготовки |
| --- | --- | --- |
| **Обычная** | Локальное, обратимое изменение с известным контрактом и без новых прав или операций записи | Один ожидаемый результат, один проверяемый источник, точечный тест/проверка и проверка затронутого поведения |
| **Сложная** | Несколько компонентов, изменение API/DTO, конкурентность, миграция данных без дополнительных разрешений или неочевидные зависимости | Краткая схема «источник → обработчик → результат», инварианты, позитивный и отрицательный сценарии, совместимость, проверка зависимости и интеграционный тест по необходимости |
| **Рисковая** | Vault/Safe Write, секреты, авторизация, внешняя запись, персональные данные, production, необратимые действия или изменение trust boundary | Основная роль + обязательный `security-reviewer` в случаях из AGENTS.md; threat/failure case, fail-closed, границы прав и состояния, отсутствие утечки, rollback/recovery; соответствующий явный owner/HUMAN_REQUIRED gate |

Если в небольшой правке обнаружилась рискованная граница, применяйте
**рисковый** уровень. Если изменились задача или разрешения — остановитесь и
уточните scope; не расширяйте его ради полноты отчёта.

## 2. Критерий готовности = наблюдение + источник

В каждом существенном критерии должны быть:

1. **Условие:** на каком входе, состоянии или действии проверяем результат.
2. **Ожидаемое наблюдение:** точное состояние, HTTP-код, исключение, отсутствие
   внешнего вызова или детерминированный артефакт. Формулировка «выглядит
   нормально» без наблюдения недостаточна.
3. **Источник доказательства:** путь к test case/fixture или строкам
   контракта, точный Git commit SHA, job/run URL при CI; для production —
   конкретный deploy SHA и проверенный health/receipt. Не заменяйте
   выполненный тест наличием тестового файла.
4. **Статус:** `PASS`, `FAIL`, `NOT_RUN`, `BLOCKED` или `UNKNOWN`.
   При `NOT_RUN` укажите недостающий инструмент или доступ, но не
   догадайтесь о результате по исходникам.

Минимальный формат в комментарии к текущей Issue/PR:

```text
Критерий: [условие] → [ожидаемый результат]
Результат: PASS | FAIL | NOT_RUN | BLOCKED | UNKNOWN
Доказательство: тест/строки контракта, exact SHA и CI run (если запускался)
Осталось: только непокрытые риски или требуемый owner gate
```

Используйте существующую Issue/PR для handoff, не заводите отдельное хранилище
evidence или новые отчётные файлы без потребности. Не публикуйте raw vault,
личные данные, prompts, токены и приватные пути в GitHub-комментариях.

## 3. Три коротких примера

**Обычная — исправлен неверный CLI-аргумент.** При ошибочном аргументе CLI
возвращает заявленный код и не меняет файл; targeted test запускается на
указанном SHA. Если запуска не было — `NOT_RUN`, даже при очевидном исправлении.

**Сложная — изменился DTO между application и Web.** Старый разрешённый
клиентский запрос обрабатывается по контракту, неверное поле отклоняется,
сохранение и отсутствие побочных действий проверены тестами. В evidence
указаны integration test, исходные контракты и exact-head CI.

**Рисковая — предложение записи в Vault.** Утверждённый preview/diff,
path containment, hash preconditions, отказ на stale input и запрет записи до
явного `--apply` доказываются отрицательными тестами с изолированной fixture.
Реальный Vault не открывается ради теста. Никакой PASS не заменяет
предусмотренный проектом человеческий допуск.

## 4. Проверка кода без второго ревьюера

До commit исполнитель делает **один ограниченный self-review** затронутого
diff и инвариантов. Затем действуют **существующие** правила
[AGENTS.md](../../AGENTS.md) и
[Night Shift](../automation/night-shift-v1.md):

- Точечные проверки во время реализации; обязательные `ruff`, `mypy`,
  `pytest` и требуемый exact-head CI — по текущему процессу.
- **Codex Code Review** возможен только после GREEN exact-head CI с
  проверкой уже существующего pending/completed review того же SHA. Round 1
  запускается максимум один раз; round 2 — **только** если исправлены
  подтверждённые блокирующие `P0/P1` одним batch. После blocking round 2
  — `HUMAN_REQUIRED`. `MEDIUM/LOW/NIT` сами по себе не запускают round 2.
- Не создавать `reviewer subagent`, второй LLM verdict или постоянный
  мониторинг. Если Codex Review недоступен, честно отмечайте `NOT_RUN` и
  выполняйте применимый human gate — не выдавайте self-review за
  независимую оценку.
- `CLEAN` review не заменяет security/privacy, release, owner approval,
  Safe Write и проверку production. Сам документ не включает Night Shift и
  не разрешает commit/push/PR/merge/deploy.

## 5. Когда остановиться

Если наблюдаемые критерии достигнуты, обязательные проверки и существующие
owner gates пройдены, остановитесь. Не превращайте локальную правку в аудит
всего репозитория, не запускайте дополнительные субагенты и не повторяйте
успешные проверки на неизменном SHA. Если критерий недоказан, оставьте
его явным, вместо формального «готово».
