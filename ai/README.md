# Second Brain Agent & Role Pack v1

Pack добавляет в `second-brain` лёгкую маршрутизацию ролей и повторяемые
агентные workflow без отдельного агентного фреймворка.

## Состав

- 6 ролей;
- 5 workflow-агентов;
- 5 готовых prompts;
- 2 eval-checklist;
- два machine-readable manifest;
- обновлённый корневой `AGENTS.md`.

## Модель

```text
Task
  -> AGENTS.md
  -> primary role
  -> optional agent workflow
  -> existing application/domain/ports/adapters
  -> safe preview/diff
  -> explicit --apply when supported
  -> vault
```

Роль отвечает за точку зрения и критерии решения.
Агент отвечает за повторяемый workflow.
Они не являются автономными сервисами и не требуют LangGraph/CrewAI.

## Где хранить

Весь pack находится в репозитории `second-brain`.

В `second-brain-vault` не копируются:

- `ROLE_MANIFEST.json`;
- `AGENT_MANIFEST.json`;
- каталог `ai/`;
- определения агентов и ролей.

Vault хранит только знания, его собственный `AGENTS.md`, конфигурацию и
Obsidian-совместимые данные.

## Как использовать Codex

Для обычной задачи достаточно описать задачу. Корневой `AGENTS.md` заставляет
Codex выбрать профиль только если он действительно нужен.

Можно вызвать workflow явно:

```text
Используй workflow inbox-processor для этой заметки. Только dry-run.
```

или:

```text
Используй роли knowledge-architect и security-reviewer.
Спроектируй изменение metadata contract, но ничего не применяй.
```

## Оркестрация разработки - отдельно от Personal Agent

Для многокомпонентных задач **разработки исходного кода** применяй существующие
роли (`knowledge-architect`, `integration-engineer`, `qa-engineer`,
`security-reviewer`) и действующий Issue/PR процесс. Руководства
[Toolkit QA Orchestra #135](https://github.com/MikeMoore1337/ai-development-toolkit/pull/135)
и [Feature Delivery Orchestra #137](https://github.com/MikeMoore1337/ai-development-toolkit/pull/137)
являются переносимыми методами; до фактического merge/публикации Toolkit и
обнаружения его инструментов клиентом **не** считать их запущенным runtime.

1. Для маленького исправления достаточно одного исполнителя; для сложной задачи
   выбираются до трёх *реально независимых* специализаций. Исследование
   domain/application, проверка контракта, security/privacy и QA по умолчанию
   **только читают разрешённый код**. В одной Issue один ответственный
   исполнитель меняет одну ветку/PR; общие модели, API, миграции и тестовые
   фикстуры не изменяются конкурентно.
2. Перед началом зафиксировать в существующем Issue неизменные критерии
   приёмки и точную ревизию кода; каждую проверку связать с конкретным
   наблюдением, средой и проверенным SHA. `PASS` отличается от `NOT_RUN`,
   `BLOCKED`, `UNKNOWN` и от последующего production. Не дублировать
   Issue в специальной БД задач и не записывать отчёты в исходники
   без прямого запроса.
3. Реальное применение отдельного агента требует существующего инструмента
   делегации и его фактического следа. Если инструмент не доступен,
   проверки выполняются последовательно (`SEQUENTIAL`), а одна модель,
   меняющая роль в рамках чата, не считается независимой экспертизой.
   Не обещать ускорение или экономию лимитов без фактических измерений.
4. Сводный handoff должен содержать исходные требования, выбранные роли,
   наблюдаемые результаты, неподтверждённое, статус отдельного ревью,
   конфликты и следующее действие. Целевой GitHub Flow и явные запросы
   на commit/push/PR/merge по `AGENTS.md` неизменны.

**Особая граница:** это разработческий процесс, **не** изменение Stage 20
Personal Agent и не Night Shift. Принятый Stage 20 Run всё ещё требует
явных действий владельца; внешние записи возможны только через
Stage 19 Prepare → Preview → Confirm → Execute → Receipt. Нет таймера,
автопродолжения, скрытого доступа к `second-brain-vault`, чтения
частных заметок, нового провайдера или прямого доступа к OS/network.

## Что pack намеренно не добавляет

- Supervisor/Manager Agent;
- LangGraph/CrewAI;
- очереди сообщений;
- отдельное хранилище состояния агента;
- автоматический commit/push;
- прямую LLM-запись в vault.
